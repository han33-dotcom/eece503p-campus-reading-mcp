# Reflection

I drew the tool boundaries around observable effects. `search_catalog` only reads a small, explicitly fictional campus catalogue. `save_reading_item` performs one durable change: adding a known book to a local reading list. Its catalogue validation protects data integrity; it does not turn the action into a second search interface. `plan_reading` owns the higher-level find-and-save workflow and calls the same domain functions used by the two primitive tools. Keeping those functions outside the MCP decorators avoids duplicating business logic and avoids unnecessary nested network requests. The orchestration result identifies both steps, its deterministic selection rule, and the actual save receipt. I chose a SQLite uniqueness constraint so retries cannot add duplicate entries, including across server restarts. The browser recording harness also needed a persistent event loop: creating a new loop for each request conflicted with the OpenAI SDK's cached asynchronous client. Reusing one loop and smoke-testing consecutive requests resolved that recording issue.

Three tools feel appropriate for this deliberately small use case: they demonstrate retrieval, persistence, and coordination without a general-purpose command tool. The limit also exposes a tradeoff: the user cannot list or remove saved items through MCP, and the lowest-ID selection rule is predictable rather than personalized. Next steps would include a real library API, user-specific storage and access controls, list inspection, and relevance-based selection. The offline demonstration validates the SDK/MCP execution path using a scripted model. The subsequent live gpt-4.1-mini run separately demonstrated correct tool selection for all three categories and an honest explanation of the no-match error. These focused scenarios complement the eighteen automated tests, but do not establish reliability for all possible natural-language requests.
